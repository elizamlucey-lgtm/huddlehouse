# Release Communications

A product update is only useful when people understand what changed and what it means for them.

Release communications help teams share important product information with customers, internal teams, and other stakeholders.

Nova helps coordinate the work. Pip checks that the details are accurate.

## 1. What belongs in release communications?

Depending on the release, communications may include:

- New features
- Improvements
- Behavior changes
- Resolved issues
- Deprecated functionality
- Required user actions
- Documentation updates
- Known limitations

Include only changes that have been confirmed by the appropriate product team.

## 2. Gather release information

Before drafting release notes, collect:

| Information | Source |
|---|---|
| Feature description | Product |
| Technical behavior | Engineering |
| Customer impact | Product and Customer Success |
| Resolved issues | Engineering and Support |
| Required actions | Product and Engineering |
| Documentation updates | Technical Writing |

Do not infer behavior from an incomplete ticket or informal conversation.

## 3. Write customer-focused release notes

A good release note explains:

- What changed?
- Why does it matter?
- Who is affected?
- Does the customer need to do anything?
- Where can the customer learn more?

### Example

**Before:**

> Updated workspace connection handling.

**After:**

> Workspace connections now provide clearer validation feedback when required configuration details are missing. Review your connection settings and update any incomplete fields before retrying.

The second example explains the user impact more clearly. In a real release, every behavior claim must be verified before publication.

## 4. Release communication workflow

1. Gather approved product changes.
2. Identify the audience.
3. Determine which documentation is affected.
4. Draft release notes.
5. Apply the Huddlehouse Style Guide.
6. Verify technical statements with Engineering.
7. Complete editorial review.
8. Coordinate publication.
9. Share the announcement with relevant teams.
10. Monitor questions and feedback.

## 5. Using AI to prepare release notes

AI can help create an initial draft from approved release information.

Example prompt:

You are helping a technical writer prepare customer-facing release notes.

Use only the supplied approved product changes.

For each change, provide:

- A clear title
- A short description
- The customer impact
- Any required customer action
- A link placeholder for related documentation

Follow the Huddlehouse Style Guide.

Do not invent product capabilities, release dates, technical behavior, or availability.

Mark unclear information as requiring confirmation.

A writer must verify and edit the draft before publication.

## 6. Release readiness checklist

- [ ] All changes are confirmed by the appropriate owners.
- [ ] Customer impact is explained clearly.
- [ ] Product terminology is consistent.
- [ ] Required actions are included.
- [ ] Affected guides and references have been reviewed.
- [ ] Technical statements are verified.
- [ ] Links have been checked.
- [ ] AI-generated content has been reviewed by a human.
- [ ] Editorial review is complete.
- [ ] Publication timing is coordinated.

## 7. After publication

Release communication does not end when content is published.

The team should:

- Share the announcement.
- Make sure Support and Customer Success know about important changes.
- Watch for customer questions.
- Identify documentation gaps.
- Correct inaccurate or incomplete information.
- Record follow-up work in Projects.

> Nova's reminder: A good release announcement tells people what changed. A great one helps them understand what to do next.
